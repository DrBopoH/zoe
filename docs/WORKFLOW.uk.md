## 1. Версія

`R.sB.C+T.hash`

| Частина | Значення |
|---|---|
| `R` | Release: мажор, росте лише за рішенням команди (ламкі зміни), а не автоматично при злитті в `main` |
| `s` | стан: `a` alpha, `b` beta, `s` stable, `m` milestone (версія, що дає реальну користь: ввід → обробка → вивід) |
| `B` | Build: номер білда (у нашому вебпроєкті білд = макротема, а не компіляція) |
| `C` | Commit: порядковий номер іменованого коміту всередині білда |
| `T` | Total: загальна кількість іменованих комітів у мажорній версії |
| `hash` | 7 символів хеша останнього атомарного коміту фічі (того, що заморожується) |

**Зворотна фіксація інкремента:** версія фіксується *перед* скиданням розряду (у SemVer — після). Тому нулів немає: перший запис `1.1.1`. Білд закрили на `1.1.29`, наступний білд почнеться з позиції `1.2.1`; так само білд 2 закрито на `1.2.113+143`, білд 3 почнеться з `1.3.1+144` (тег заморожування білда 2 — `v1.s2.113+143`) (`C` обнуляється, `T` іде далі). Вихід іменованого білда: `B+1`, `C` скидається; реліз: `R+1`, `B` і `T` скидаються.

Стан росте зліва направо: `a → b → s → m`; `a` найчастіше, із `s` не поспішаємо. Літеру білду присвоює команда. До користувача зазвичай доходить `R.sB` або `R.sB.C`; `+T.hash` потрібні розробникам.

**Літера стану є лише в гілках вище `dev`** (`build`, `main`, `fix`). На `dev` версія без літери: `v1.1.29+29`.

Приклади: `v1.1.29+29.3487fe9` (іменований коміт на `dev`), `v1.b1.29+29.8ac5080` (заморожування білда).

## 2. Дві зони: local і remote

**Локально (trunk-based, модифікований).** Одна гілка `<модуль>/<дата>-<слово>` на одну фічу (модуль — набір фіч одного контексту: `ui`, `candles`, `binance`, `sources`, `macro`, `docs`, `tooling`…; списку немає, підійде будь-яке латинське слово, крім службових імен гілок на кшталт `dev` чи `build`; `./clc.sh modules` показує, що вже є); атомарні коміти, шум дозволено (видалити, повернути, переписати — це особиста історія). Атомарні коміти й гілка модуля лишаються лише на твоїй машині (на `origin` пушиться сама гілка модуля для PR, але в `dev` потрапляє один стиснений коміт).

**Віддалено.** Захищені гілки: жодних авторських push, force-push і локальних merge-push; усе йде через PR, перевірки CI та рев'ю. У `dev` PR вливається **Squash**: усі атомарні коміти фічі перетворюються на один **іменований (заморожений) коміт**.

Іменований коміт: `зведення фічі | vR.B.C+T.<hash7>`, де `hash7` — короткий хеш останнього атомарного коміту гілки. Одна гілка = одна фіча = один іменований коміт.

> Наслідок Squash: на графі `dev` іде однією лінією іменованих комітів, а гілки модулів висять поруч (у squash-коміту немає батька на вершині гілки). Це не помилка. Чиста лінія версій: `git log --first-parent dev`.

## 3. Гілки та правила GitHub

| Гілка | Що це | Спосіб злиття |
|---|---|---|
| `<модуль>/<дата>-<слово>` | робоча гілка фічі модуля (старі `wip/…` — того самого виду) | локальна |
| `dev` (default) | потік іменованих комітів, без літери | **Squash** only |
| `build` | заморожування білдів | **Merge commit** only |
| `main` | лінія релізу (поки демонстраційна; опційно окрема `release` для тегів) | **Merge commit** only |
| `fix` | дубль `dev` для хотфіксів (план) | захищена від force-push |

Ruleset на `dev`, `build`, `main`: заборона видалення, заборона force-push, обов'язковий PR (approvals: 0), обов'язкові перевірки `backend`, `frontend`, `hygiene`. Не вмикати «Require branches to be up to date» і «Linear history» (мерж-коміти білда потрібні). Для PR увімкнено автовидалення head-гілок; default-гілка — `dev`.

## 4. Коміти

- **Атомарні:** Conventional Commits `тип: що зроблено`, **англійською**, наказовий спосіб, малими літерами, не довше 72 символів після `тип: `. Типи: `feat`, `fix`, `refactor`, `perf`, `test`, `docs`, `style`, `chore`; ламка зміна `feat!: …`. Версію в них не пишуть.
  Приклади: `feat: add render pipeline`, `fix: lift bans on cards when IBAN is relinked`.
- **Іменовані** (з'являються при PR): `Зведення | vR.B.C+T.hash7`. Кожен такий коміт збільшує `C` і `T`.
- Один коміт = одна логічна правка, що збирається й проходить тести. Не змішуй бекенд, фронт і рефакторинг в одному коміті.
- До репозиторію не потрапляють `*.db`, `.env`, ключі, виписки, архіви (CI перевіряє, `clc.sh` не дає додати в індекс).

## 5. Життя фічі

```bash
git fetch -q && ./clc.sh next <модуль> <слово>      # нова гілка модуля від свіжого origin/dev
# ...правки...
./clc.sh ship all "feat: add thing" -z "Thing: що вийшло" -f
```

`ship` сам робить: застосовує патчі з `~/Downloads/patch*.zip`, ганяє перевірки (`go test`, збірка фронту), комітить; `-z "зведення"` далі відкриває PR у `dev` із заголовком-іменованим комітом, чекає перевірки й вливає Squash. Після цього `./clc.sh next <модуль> <слово>` починає наступну фічу від свіжого `dev`, а не від вершини минулої гілки.

Перша фіча нового білда відкривається з `-v R.B`, наприклад `./clc.sh ship all "feat: …" -z "Зведення" -v 1.3`: `C` обнуляється, `T` іде далі (`next_version`). Усередині білда `-v` не потрібен.

Потрібно лише доповнити вже закомічене: `./clc.sh amend <scope>` (поки коміт не на remote).

## 6. Білд

Білд = зліпок останнього іменованого коміту `dev`, **без правок вихідних кодів**, поки не зібрано стійкий продукт. У нас немає компіляції, тому «збірка» = `go test` + `bun run build` + ручна перевірка в UI.

```bash
./clc.sh build            # бета (b): PR dev → build, Merge commit, тег
./clc.sh build a          # інша літера (a|b|s|m)
./clc.sh build s "Build 2: макро і ринок"   # власна назва; тег рахується за вершиною dev
```

Що робить `build`:
1. Бере вершину `origin/dev` (вона має бути іменованим комітом) і рахує версію: `C` і `T` не рухаються, додається літера (`v1.1.29+29` → `v1.b1.29+29`).
2. Чекає, поки CI на цьому коміті завершиться, і ріже білд, лише якщо все зелене.
3. Відкриває (або знаходить) PR `dev → build` і чекає перевірки саме цього PR.
4. Вливає його **Merge commit** із заголовком `Build 1 beta | v1.b1.29+29.<hash7 вершини dev>`: на `build` з'являється іменований коміт заморожування з літерою, другим батьком у нього вершина `dev`.
5. Ставить анотований тег `v1.b1.29+29` на цей коміт.

Якщо в `dev` немає нічого нового відносно `build`, заморожувати нічого. Нових гілок команда не створює.

## 7. Хотфікс і реліз (план)

Команда `hotfix` поки не реалізована; схема така:

- **Хотфікс білда:** баг, знайдений під час тестування, правиться в `build` (додатковий інкремент) через гілку `fix` (дубль `dev`) або прямо в `build`. Версія `R.sB-F.C+T.hash`, наприклад `1.a1-3.29`: число після «−» (номер перезбірки білда) росте; `C` **не** рухається; `T` росте. Хотфікс не відкриває новий білд. Після хотфіксів `fix` вливається в `dev` іменованим комітом через PR: виправлення повертається в основний потік.
- **Реліз:** вдалі білди, які команда вирішила опублікувати, вливаються в іменований коміт релізу в `main`. `R` росте лише за рішенням команди.

## 8. clc.sh

Помічник у корені репозиторію (потрібен `7z`, для PR — `gh`). Докладна довідка: `./clc.sh help`.

| Команда | Що робить |
|---|---|
| `ship <be\|fe\|docs\|all> "тип: що" [-b модуль/слово] [-p] [-f] [-n] [-z "зведення"] [-v R.B]` | гілка → `apply` → перевірки → коміт → (`-z`) PR і злиття |
| `commit <scope> "тип: що" [-n] [-b модуль/слово]` | перевірки → коміт (без `apply`) |
| `apply [--force]` | усі `patch*.zip` з `~/Downloads` по черзі, у кожного знімок «до» в `.commits/applied/` |
| `rollback [list\|N]` | повернути `backend/` і `frontend/` до застосування N-го патча |
| `init` | завести `.commits/`, `.claude` і рядки в `.gitignore` |
| `land "зведення" [-v R.B]` | влити гілку модуля в `dev` одним іменованим комітом; за наявності remote робить те саме, що `done` |
| `branch <модуль> <слово>` / `next <модуль> <слово>` | гілка модуля від свіжого dev (`next` ще робить `fetch`); нове ім'я модуля друкується разом з наявними, тож описка помітна |
| `modules [модуль]` | модулі, за якими є гілки (локальні й `origin`): скільки й коли остання; з іменем — гілки модуля |
| `pr "зведення" [-v R.B]` | push + PR у `dev` із заголовком-іменованим комітом |
| `merge` | дочекатися перевірок PR → Squash and merge → локальний `dev` ← `origin/dev` |
| `done "зведення"` | `pr` + `merge` |
| `build [a\|b\|s\|m] ["зведення"]` | заморожування білда (див. §6) |
| `publish` | `git push -u origin <гілка модуля>` |
| `amend`, `undo` | доповнити останній коміт; зняти його (правки лишаються в індексі) |
| `park`, `unpark` | сховати й повернути незакомічене |
| `good`, `restore` | мітка робочої версії після перевірок і повернення до неї |
| `look`, `run`, `push` | знімок репозиторію в `.claude`, запуск команди із записом виводу, пакет файлів для чату |
| `sw <гілка>`, `drop <гілка> [-f]` | перейти / видалити локальну гілку |

Scope у `ship`/`commit`: `be` (лише `backend/`), `fe` (`frontend/`), `docs` (лише `*.md` і `.github`), `all` (усе, крім непотрібного). Прапорці: `-p` запушити пакет, `-f` застосовувати патчі при нечистому дереві, `-n` без перевірок.

Скрипт захищає репозиторій: бази, ключі та `.env` знімаються зі стейджу, комітити напряму в `dev`/`build`/`fix`/`release` не можна.

## 9. CI

`.github/workflows/ci.yml` запускається на кожен PR і push у `dev`, `build`, `main` (нове надсилання скасовує застарілий прогін):

- **backend:** `gofmt -l` (дерево зобов'язане бути відформатованим), `go vet`, `golangci-lint` (версію закріплено, v2.15.0; конфіг `backend/.golangci.yml`), `go test ./... -count=1`, `go build`;
- **frontend:** `bun install --frozen-lockfile`, `bun run test` (`node --test` для логіки та vitest для компонентів), `bun run build`;
- **hygiene:** немає баз, ключів, архівів (`.db`, `.sqlite`, `.pem`, `.key`, `.p12`, `.zip`), `.env`, `.commits/`, `.claude`; немає секретів (`AKIA…`, `ghp_…`, приватні ключі); немає 16-значних чисел, схожих на номер картки, у `backend` і `frontend/src` (тестові заглушки заведено в allowlist усередині `ci.yml`).

Ці три job'и — обов'язкові перевірки в ruleset.

## 10. Що перед «готово»

1. `cd backend && go test ./...`, `gofmt -l .` без виводу і `golangci-lint run` без зауважень.
2. `cd frontend && bun run test && bun run build`.
3. Нові парсери й правила — тести на анонімних даних, включно з повторним імпортом (без дублів).
4. Жодних персональних даних у фікстурах і документації: вигадані імена, номери із зірочками.
5. Правиш пару «Go ↔ JS» (`idKey`, `looseKey`, `isPanLike`, індекс кешу) — правуй обидві сторони.
